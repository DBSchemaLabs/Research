# Do prepared statements survive the schema change?

Date: Oct 7, 2026  
Setup: PostgreSQL 16 on macOS, a small dedicated database.  
Script and log: [Benchmarks · Experiment #7](https://github.com/DBSchemaLabs/Benchmarks/tree/main/experiment-phase-1/e7-prepared-statements)

### Why

Apps rarely send fresh SQL every time. Drivers and pools prepare statements and reuse them. If a statement was prepared before the migration, what happens when it runs after?

## E7 — Prepare, change the schema, run again

I prepared `SELECT status FROM orders WHERE id = 1`, made each of the two changes I've tried so far, and ran the same statement again. In the first test the view returns a different value from the table, so I could tell which one was read.

| Change | Before | After |
|---|---|---|
| E3: rename the table, put a view in its place | `from-old-table` | `from-new-view` |
| E1: change the column type in place | `paid` | Error: `cached plan must not change result type` |

**The view swap was invisible.** The prepared statement followed the name to the new view and returned its value, with no error. Postgres re-planned the statement against whatever `orders` now is.

**The type change broke it.** The result column went from TEXT to the enum, and Postgres won't run a cached plan whose result type changed. Re-preparing fixed it. But with a connection pool, every connection that prepared this statement before the ALTER would get one error after it.

**So E3 wins on this one, with a condition.** It worked because the view keeps `status` as TEXT. If the view's column type changed, I'd expect the same error.
