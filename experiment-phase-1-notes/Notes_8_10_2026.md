# What can't you do through the view?

Date: Oct 8, 2026  
Setup: PostgreSQL 16 on macOS, the E3 database (`orders` is now a view over `orders_base`).  
Script and log: [Benchmarks · Experiment #8](https://github.com/DBSchemaLabs/Benchmarks/tree/main/experiment-phase-1/e8-view-limits)

### Why

E3 only tested insert, update and select through the view. Apps and their tools do more than that, so I tried five other common operations against `orders`.

## E8 — Five table operations against the view

| Operation | Result |
|---|---|
| Upsert (`INSERT ... ON CONFLICT`) | Error |
| Row lock (`SELECT ... FOR UPDATE`) | Works |
| `COPY` into it | Works |
| `TRUNCATE` | Error |
| `ALTER TABLE ... ADD COLUMN` | Error |

**Upserts break.** This is the one that worries me most, because apps use `ON CONFLICT` all the time. The primary key is on `orders_base`, and the view has no unique constraint for `ON CONFLICT` to match. The error comes back as soon as the query runs, so at least it isn't silent.

**COPY and row locks still work.** COPY goes through the INSTEAD OF trigger one row at a time, which E6 suggests will be slower than a plain table.

**The tooling around the app breaks too.** TRUNCATE (often used in test cleanup) and ALTER TABLE (the next migration, or an ORM's schema sync) both reject the view. Anything that manages the schema now has to know about `orders_base`.

**One thing to test later.** `FOR UPDATE` through a join view probably also locks the matching `order_status` row. If it does, two transactions locking different orders with the same status could block each other.
