# Readers stuck behind a waiting ALTER

Date: Oct 9, 2026  
Setup: PostgreSQL 16 on macOS, a dedicated database with 100,000 orders.  
Script and log: [Benchmarks · Experiment #9](https://github.com/DBSchemaLabs/Benchmarks/tree/main/experiment-phase-1/e9-lock-queue)

### Why

E3's cutover took 36 ms, but I noted that this didn't tell me how long application queries were blocked. E3 also used a `lock_timeout` without my knowing what it protects against. This experiment looks at that directly.

## E9 — A slow read, then an ALTER, then a tiny read

A report-style read held `orders` open for 4 seconds. While it ran, I started an `ALTER TABLE ... ADD COLUMN`, then a primary-key lookup for a single row.

| | Without `lock_timeout` | With `lock_timeout = '200ms'` |
|---|---:|---:|
| What happened to the ALTER | Waited for the slow read | Gave up after 200 ms |
| Single-row read | **2,978.875 ms** | **0.740 ms** |

**The tiny read waited almost 3 seconds, and it wasn't waiting for the slow read.** Its lock is compatible with the slow read's. The lock snapshot shows it queued behind the ALTER, which was itself queued behind the slow read. Every new query on the table joins that queue.

**The ALTER didn't need to do any work.** Adding a nullable column is metadata-only, so the change itself is instant. The waiting is what hurts.

**`lock_timeout` swaps stalled reads for a failed ALTER.** With it, the read took under a millisecond, but the ALTER errored and would need a retry.

So E3's 36 ms cutover isn't the whole story. Its `lock_timeout = '2s'` means readers could wait up to 2 seconds on each attempt if a long transaction was open.
