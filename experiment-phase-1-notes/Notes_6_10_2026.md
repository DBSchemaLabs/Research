# Does the view still use an index?

Date: Oct 6, 2026  
Setup: PostgreSQL 16 on macOS, the E3 database (about 2 million orders behind the `orders` view).  
Script and log: [Benchmarks · Experiment #5](https://github.com/DBSchemaLabs/Benchmarks/tree/main/experiment-phase-1/e5-view-index)

### Why

In Entry #2 I noted the count query through the view was slow, but said I needed a before/after comparison before blaming the view. So this time I asked the same question two ways: once through the view, once directly on the table underneath.

## E5 — A rare status, through the view vs directly

I added a `refunded` status with just 50 orders and indexed `orders_base(status_id)`. Then I fetched those 50 rows.

| Measurement | Through the view | Directly on `orders_base` |
|---|---:|---:|
| Plan | Parallel sequential scan + hash join | Index scan |
| Rows scanned | ~2 million | 50 |
| Buffers touched | 23,109 | 5 |
| Estimated rows | 1,527 | 1 |
| Execution time | 70.423 ms | 0.015 ms |

About **4,700× slower** for the same 50 rows.

**The index works. The view just doesn't reach it.** The direct query uses the index. Through the view, Postgres read the whole table.

**The planner can't see through the name.** The view filters on `status = 'refunded'`, which only becomes `status_id = 5` after joining the lookup table. At plan time Postgres doesn't know which id it'll be, guessed about 1,500 rows, and picked a full scan.

**So the translation isn't free on reads either.** E3 showed the view keeps queries working. E5 shows a selective query can still lose the index, and the app gets no error, just a slow query.

# What does the write trigger cost?

Date: Oct 6, 2026  
Setup: PostgreSQL 16 on macOS, the E3 database (about 2 million orders behind the `orders` view).  
Script and log: [Benchmarks · Experiment #6](https://github.com/DBSchemaLabs/Benchmarks/tree/main/experiment-phase-1/e6-write-overhead)

### Why

Entry #2 ended with "the translation didn't disappear... need to measure what that costs." E5 measured it on reads. This measures it on writes.

## E6 — 20,000 inserts, three ways

I timed 20,000 single-row inserts into a plain TEXT table, into `orders_base` directly, and through the `orders` view, rolling back each time.

| Target | Time | vs plain table |
|---|---:|---:|
| Plain TEXT table | 34.892 ms | 1.0× |
| `orders_base` directly | 134.606 ms | 3.9× |
| Through the `orders` view | 176.268 ms | 5.1× |

**5× slower through the view, but the trigger isn't most of it.** If I'd only compared the plain table with the view, I'd have blamed the whole 5× on the translation. The middle row shows writing straight into `orders_base` is already 3.9× slower. The trigger's own share is about 30% of the gap, roughly 2 µs per insert.

**The table underneath costs more than the view.** `orders_base` has 2 million rows, a foreign key, a CHECK constraint and an extra index. The plain table had none of that. I haven't split those costs apart yet.

**In a real app, round trips would hide this.** The loop ran inside Postgres. An app pays a network round trip per insert, which is far more than 2 µs.
