# Is the enum really transparent?

Date: Oct 5, 2026  
Setup: PostgreSQL 16 on macOS. One TEXT table and one ENUM table, each holding the four status values once.  
Script and log: [Benchmarks · Experiment #4](https://github.com/DBSchemaLabs/Benchmarks/tree/main/experiments/e4-enum-semantics)

### Why

In E1 I wrote that the basic queries still worked after converting `status` to an enum. I'd only tried equality with a literal, an insert, an update and a concatenation, so this time I ran a wider set of queries an app might use against both types.

## E4 — Same queries, TEXT vs ENUM

| Query | TEXT | ENUM |
|---|---|---|
| `status = 'paid'` | 1 row | 1 row |
| `status LIKE 'p%'` | 2 rows | Error |
| `status = lower('PAID')` | 1 row | Error |
| `ORDER BY status` | cancelled, paid, pending, shipped | pending, paid, shipped, cancelled |
| `status > 'paid'` | pending, shipped | cancelled, shipped |
| Prepared with a `text` parameter | 1 row | Error at PREPARE |
| Prepared with an untyped parameter | — | 1 row |

Only the string literal behaved the same.

**Some queries fail loudly.** `LIKE` and `lower()` both produce TEXT, and there's no operator between `order_status` and `text`. At least the app would see the error.

**Some fail silently.** `ORDER BY` follows the order the enum values were declared in, not the alphabet, and `> 'paid'` returns a different pair of rows. Nothing errors. The app just gets different answers. These worry me more.

**It depends on the driver.** A statement prepared with a `text` parameter can't even be prepared against the enum. Leave the parameter untyped and Postgres infers the enum, so it works. Same SQL, different outcome, depending on how the driver sends strings.

### Correcting Entry #2

"The basic queries still worked" was true only for the queries I tried. The enum translates string literals and nothing else. It isn't a drop-in replacement for TEXT.
