# Changing status without changing the app

Started: Oct 4, 2026  
Setup: PostgreSQL 16 on macOS, 2 million rows.

### Objective

Store orders.status as integers instead of text (pending, paid, shipped, cancelled), while keeping the database live and existing application queries unchanged.
I started with an enum, then tried moving the conversion behind a view.

## E1 — Just ALTER the column

Converted `status` from TEXT to a PostgreSQL enum.

| Measurement | Result |
|---|---:|
| Conversion | 2.214 s |
| Table size | 88 MB → 85 MB |
| Filenode | 16437 → 16455 |

The filenode changed, so Postgres rewrote the table. Only saved about 3 MB here, less than I initially expected.

The basic queries still worked:
- `WHERE status = 'paid'` returned 500,000 rows.
- Inserts and updates with valid status names worked.
- String concatenation returned `shipped_x`.



## E2 — What happens to a read during ALTER?

Ran the same conversion in the background, then tried a small primary-key read: `id < 10`.

| Measurement | Result |
|---|---:|
| ALTER | 3.040 s |
| Read during ALTER | 2.712 s |
| Same read afterward | 0.525 ms |
| Rows returned | 9 |

The lock snapshot showed a granted `AccessExclusiveLock`.

The read got the right answer, but waited for the remaining rewrite. Even fetching nine rows couldn't get past it.

## E3 — Keep the old interface, change storage underneath

Tried expand/contract inside the database:

1. Added a lookup table mapping status names to SMALLINT IDs.
2. Added `status_id` and a trigger to keep it in sync with `status`.
3. Backfilled in batches of 100,000 while another client ran inserts and updates.
4. Added and validated a non-null CHECK and a foreign key, then ran ANALYZE.
5. Renamed the table to `orders_base`, dropped the text column, and put an `orders` view in its place. An INSTEAD OF trigger translated writes.

The last step happened in one transaction, with a short lock timeout.

| Measurement | Result |
|---|---:|
| Initial rows | 2,000,000 |
| Initial insert | 4.315 s |
| Add nullable column | 0.103 ms |
| Backfill | 5.136 s |
| Mapping inconsistencies found | 0 |
| Cutover, measured from client | 36 ms |
| Concurrent writer iterations | 144 |
| Final rows | 2,000,142 |
| Filtered count | 83.541 ms |
| Table size | 88 MB → 184 MB |
| Estimated dead tuples afterward | 0 |

The tested reads and writes worked through the view, and the mapping checks found no inconsistencies.

**A couple of things stood out:**

**The table got bigger.** About 2.1× its original size after backfill. UPDATEs created new row versions, and dropping the text column didn't immediately give the space back. The dead-tuple estimate was zero, but allocated space is a separate thing. These sizes exclude indexes.

**The count query had a poor estimate.** The plan used a parallel sequential scan and hash join, with about 636 matching rows estimated versus 166,701 actual per participant. Need a before/after comparison before blaming the view for the query time.

**The translation didn't disappear.** It's now in the lookup join and write trigger. Need to measure what that costs.
