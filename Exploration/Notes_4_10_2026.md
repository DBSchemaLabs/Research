## Possible Approaches to address Cut-over times & Read/Write Waits

Here are few things I found while exploring the answers online - 

| System | What it does                                                                                                                |
|---|-----------------------------------------------------------------------------------------------------------------------------|
| pgroll | Automates expand/contract and exposes schema versions through views. Close to what I tried manually.                        |
| MySQL + gh-ost / pt-online-schema-change | Different ways of copying data and keeping a replacement table in sync. Need to check support for the actual value mapping. |
| Oracle DBMS_REDEFINITION | Native online redefinition with column mappings.                                                                            |
| Oracle EBR | Editioning views and crossedition triggers let different application versions coexist.                                      |
| SQL Server | Supports online ALTER COLUMN for some operations. Need to check whether this conversion qualifies.                          |
| Dictionary-encoded storage | Maybe storing repeated strings compactly doesn't need a logical schema change in the first place.                           |

## Things I've picked up from the docs

### PostgreSQL

Some type changes avoid a rewrite, but the TEXT-to-ENUM conversion I tested didn't.

Adding a nullable column without a default avoids rewriting existing rows. It still needs a lock though — metadata-only isn't the same as lock-free.

CHECK and foreign-key constraints can be added as NOT VALID and checked separately. For the non-null check, I used `CHECK (status_id IS NOT NULL)`, not `NOT NULL ... NOT VALID`.

### pgroll

Applications access schema versions through views, selected using search_path.

That might be a connection or role configuration change rather than a source-code change. Need to be precise about what “no app changes” allows here.

### MySQL

The MySQL 8.0 docs say changing a column's data type requires ALGORITHM=COPY. Other operations have different rules.

Need to compare the native path with gh-ost and pt-online-schema-change, including what happens to old writes during cutover.

### Oracle

DBMS_REDEFINITION and EBR both look relevant, but they solve different parts of the problem.

Want to understand the setup required, remaining locks, and what clients need to know. “Native support” alone doesn't answer whether the old app survives this particular change.

### SQL Server

Online ALTER COLUMN exists, with restrictions. Need to check the exact conversion and supported environment before treating it as a solution.

## Other ideas

### A custom Postgres type

Could it accept and return text, but store a small integer?

Sounds appealing, but input/output functions are only part of compatibility. What type does the driver see? Which operators work? And how does existing data get converted?

### Logical replication

Copy into a new representation while changes keep arriving, then switch over.

Need to look at transformation support, lag, transaction consistency, sequences, and the client cutover. May just move the hard part somewhere else.

### A different cutover

Could partition-based techniques help instead of renaming a table?

Not sure they fit this transformation. Worth checking dependencies and locks before spending much time on it.

### Storage encoding instead of schema change

If the goal is just to avoid storing the same words repeatedly, dictionary encoding is worth reading about.

It addresses the storage question. Doesn't necessarily help with more general schema changes.
